# Лабораторная работа №6 — GitLab, nginx, SSO и приключения с runner 🙂

## Часть 1 — Собираем стенд

Для этой лабы мы поднимаем локальный GitLab и собираем вокруг него небольшой DevOps-стенд. Подключаем единый вход через Keycloak, ставим nginx перед сервисами, настраиваем CI/CD и добавляем мониторинг. По дороге ловим несколько багов и знакомимся с логами поближе 😅

Всю инфраструктуру складываем в каталог `lab6`. Приложение используем из прошлой лабы — сервис заметок на Flask, который уже лежит в `lab4/app`. Dockerfile и зависимости берём оттуда же, поэтому в конфиге CI появляются относительные пути к `../lab4/app`.

Настройку источника данных Grafana тоже переиспользуем из четвёртой лабы. В `compose.yaml` подключаем каталог `../lab4/monitoring/grafana/provisioning/datasources`. Так у нас остаётся одна версия общих файлов, и правки не приходится размазывать по нескольким папкам 👍

Основные сервисы запускаем через Docker Compose. В стенд входят GitLab CE, Keycloak, nginx, Grafana, Prometheus, nginx-exporter и статический GitLab Runner. Для динамических заданий отдельно используем Kubernetes-кластер kind.

Для сервисов настраиваем локальные домены `gitlab.lab.test`, `registry.lab.test`, `sso.lab.test` и `grafana.lab.test`. Внутри Docker они ведут на внешний nginx с адресом `172.30.6.10`.

Пароли и секреты передаём через переменные окружения. Для запуска Compose нужны `GITLAB_ROOT_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, `GRAFANA_PASSWORD`, `GITLAB_OIDC_SECRET`, `GRAFANA_OIDC_SECRET` и `TEST_USER_PASSWORD`. Рабочий `.env` оставляем локально.

### Первый квест с сертификатами

Сертификаты генерируем скриптом `make-certs.sh`. Мы создаём локальный центр сертификации и подписываем им серверный сертификат для четырёх доменов стенда.

На первом запуске GitLab ловим `Read-only file system`. Причина оказалась в монтировании сертификата в `trusted-certs` с запретом записи. Во время настройки GitLab пытался обработать этот файл, а файловая система отвечала отказом. Старт уже получился бодрый 🙃

Фиксим монтирование и подключаем целый каталог `certs/gitlab-trusted` с возможностью записи. Конфиг GitLab при этом продолжаем подключать отдельно в режиме чтения.

Следом получаем ошибку `curl (77)`. Команда искала `certs/ca.crt`, пока терминал находился в корне репозитория. Переходим в `lab6` и используем путь относительно текущей папки. В этой лабе расположение терминала неожиданно становится полноценным участником команды 😄

## Часть 2 — Подключаем Keycloak

В `keycloak/realm.json` описываем realm `lab6`, пользователя `student` и два OIDC-клиента — `gitlab` и `grafana`.

Realm в нашем стенде объединяет пользователей и настройки входа. Клиенты описывают приложения, которым Keycloak разрешает использовать эту авторизацию.

Для каждого клиента задаём свой секрет и адрес возврата. После входа в Keycloak браузер должен вернуться в нужный сервис, поэтому callback для GitLab и Grafana различается.

В GitLab подключаем провайдер `openid_connect` через OmniAuth. В Grafana используем Generic OAuth. Оба приложения обращаются к realm `lab6`, а локальный CA добавляем в доверенные сертификаты.

Сам флоу входа получается таким. Мы открываем приложение, нажимаем Keycloak и переходим на его форму. После проверки учётки Keycloak возвращает браузер с кодом авторизации. Приложение обменивает код на токены, проверяет их и создаёт свою сессию.

На первом рисунке фиксируем форму нашего realm. Экран входа уже загрузился, можно вводить учётку 🙂

После входа попадаем на стартовую страницу GitLab. На втором рисунке видим приветствие пользователя Lab и возможность создать проект. Авторизация пустила нас в интерфейс, первый чекпоинт пройден ✅

### Как мы случайно сломали привязку

При подготовке скриншота нам понадобилось снова увидеть форму пароля. Keycloak уже запомнил сессию и пропускал нас автоматически. Мы отвязали провайдер в настройках GitLab и получили `Email has already been taken`. Получился небольшой самострел 😅

В GitLab уже существовал пользователь с такой почтой. После удаления привязки новый вход через провайдера столкнулся с этой учёткой. В конфиг добавляем `omniauth_auto_link_user` для `openid_connect`, чтобы восстановить связывание в нашем учебном стенде.

Для повторного показа формы дальше используем приватную сессию браузера. Автоматический переход при действующей сессии Keycloak как раз укладывается в идею SSO.

Заодно разбираемся с паролями. Администратор Keycloak, локальный администратор GitLab и пользователь `student` — отдельные учётки. При входе в локальную форму GitLab пароль от админки Keycloak нам не помогает.

## Часть 3 — Ставим nginx перед сервисами

Внешний nginx принимает запросы к доменам стенда и проксирует их во внутреннюю Docker-сеть. TLS завершается на nginx, а до сервисов запросы идут по внутренним адресам.

В конфиге включаем перенаправление с HTTP на HTTPS. Дополнительно выбираем два правила доступа.

Первое правило ограничивает `/admin`. В `admin-allow.conf` разрешаем адрес `172.30.6.1`, остальные адреса блокируем. Это адрес, с которого nginx видит разрешённые запросы в нашем локальном окружении.

Второе правило ограничивает обращения к `/users/sign_in`. Настраиваем темп пять запросов в минуту и небольшой допустимый всплеск `burst=5`. При превышении лимита nginx возвращает `429`.

Админку ограничиваем, чтобы чувствительные функции были доступны только с нужного адреса. Лимит страницы входа помогает сдерживать частые запросы к ней. В нашем стенде вход через Keycloak имеет отдельный маршрут, поэтому этот лимит относится именно к странице GitLab `/users/sign_in`.

Для первой проверки запускаем временный контейнер с `curl` в сети `lab6-net` и адресом `172.30.6.250`. Запрос к закрытому разделу получает `403`. Затем отправляем серию запросов на страницу входа и видим переход от `200` к `429`. nginx включил режим фейс-контроля 🙂

## Часть 4 — Настраиваем runner и pipeline

Для CI выбираем два типа runner. Статическому отдаём проверку синтаксиса и сборку Docker-образа. Параллельные тесты отправляем в Kubernetes.

Такое распределение подходит нашему стенду. Для сборки заранее настраиваем Docker, доступ к registry и доверие к сертификату. Тестовые задания удобно запускать в отдельных pod и выполнять одновременно.

### Статический runner

Статический runner запускаем сервисом `runner-static` через профиль `ci`. Используем Docker executor и тег `static`.

Скрипт `runners/make_static_template.py` генерирует шаблон регистрации. В нём задаём сеть `lab6-net`, ограничение на одно задание и подключение сертификата registry. Для сборки через Docker-in-Docker включаем привилегированный режим контейнеров заданий.

На регистрации сначала спотыкаемся о ввод токена. Команда `read -rsp` была рассчитана на Bash, а наш терминал работал в zsh. Получаем `read -p no coprocess` и продолжаем разбор полётов 🙃

Для zsh меняем ввод на подходящий вариант и явно передаём токен в параметр `--token` при регистрации runner. До успешной регистрации рабочего `config.toml` не было, поэтому runner жаловался на отсутствующий файл.

После регистрации конфиг сохраняется в подключённом каталоге. Сам файл содержит токен, поэтому в Git его не отправляем.

### Динамический runner

Для динамических заданий создаём кластер kind с именем `lab6` и namespace `lab6-ci`. Узел кластера подключаем к Docker-сети `lab6-net`, чтобы задания могли обращаться к GitLab через nginx.

Через Helm устанавливаем GitLab Runner с Kubernetes executor. CA передаём в Secret `lab6-ca`, токен — в Secret `lab6-runner-token`. Настройки храним в `runners/dynamic/values.yaml`.

В конфиге выставляем `concurrent=3`. Это позволяет управляющему runner обрабатывать до трёх заданий одновременно.

Один раз повторно запускаем создание уже существующего кластера и получаем сообщение, что узлы `lab6` уже есть. Здесь просто продолжаем работу с готовым кластером. Пересоздавать его ради повторной команды не понадобилось 🙂

Проверяем регистрацию через логи deployment.


На рисунке 4 видим `Runner registered successfully` и загрузку конфигурации. Предупреждение про `user-mode` тоже есть, дальше процесс runner запускается и начинает работу.

### Собираем задания CI

Основной pipeline описываем в `lab6/.gitlab-ci.yml`. Корневой `.gitlab-ci.yml` подключает его через `include`, поэтому GitLab находит конфигурацию при пуше всего репозитория.

В pipeline делаем два этапа — `check` и `build`.

Задание `syntax` запускает проверку Python-файлов приложения и тестов через `compileall`. Оно получает тег `static`.

Задание `unit-tests` получает тег `dynamic` и параметр `parallel=3`. Каждый экземпляр устанавливает зависимости из `../lab4/app/requirements.txt` и запускает набор тестов из `lab6/tests`.

В тестах проверяем открытие главной страницы, отказ при пустой заметке, ограничение размера нагрузочного запроса и обработку недоступности БД. Для последнего сценария используем mock подключения, поэтому реальную базу для этих unit-тестов поднимать не требуется.

Все три параллельных задания выполняют один и тот же набор тестов. Такое повторение помогает нам показать параллельную работу runner. Разбиение тестов на разные части здесь не реализуем.

В задания добавляем `sleep 45`, чтобы успеть увидеть pod в работе. Поэтому длительность джоб включает искусственную паузу и не подходит для честного бенчмарка скорости 🙂

Задание `build-image` запускается на статическом runner. Оно собирает образ из `../lab4/app` и отправляет его в GitLab Container Registry. В качестве тега используем короткий идентификатор коммита.

### Ловим баги перед зелёным pipeline

При локальном запуске тестов сначала используем Python 3.14 и получаем ошибку установки `psycopg-binary==3.2.9`. Следом тесты падают с `ModuleNotFoundError`. Для совместимого запуска ориентируемся на Python 3.12, который уже указан в Dockerfile и CI.

Отдельный квест появляется с `git push`. Команда долго висит без понятного запроса учётных данных. Для отправки используем терминальный ввод, отключаем askpass-помощники VS Code для этой команды и указываем CA GitLab. После этого репозиторий удаётся отправить.

Ещё нас сбивает пустой вывод `git diff --cached --name-only`. Проверяем `git status` и видим чистое рабочее дерево. Файлы уже были закоммичены, поэтому список подготовленных изменений закономерно пустой.

Первый pipeline остаётся без журналов и заканчивается ошибкой после долгого ожидания. У статического runner замечаем HTTP `500` при отправке trace. Идём в логи GitLab и находим причину.

```text
CI job token signing key is not set
```

Для фикса через `gitlab-rails runner` проверяем `ApplicationSetting.current` и создаём отсутствующий RSA-ключ подписи CI job token. Затем перезапускаем службы GitLab. Это отдельное административное восстановление состояния GitLab, которое выполняем вручную внутри контейнера.

После исправления ключа журналы заданий становятся доступны. Теперь дебаг хотя бы разговаривает с нами человеческими логами 😅

У динамических заданий находим другую проблему. Kubernetes пытается скачать helper-образ `x86_64`, хотя узел работает на ARM64. В событиях видим `no match for platform in manifest`.

В Helm values добавляем выбор узла с архитектурой `arm64` и ОС `linux`, затем обновляем release. После фикса pod начинают проходить инициализацию и переходят в `Running`.

## Часть 5 — Повторно проверяем HTTPS и правила доступа

После фиксов CI возвращаемся к nginx и фиксируем результаты отдельными проверками.

Сначала отправляем HTTP-запрос.

```bash
curl --max-time 15 -I http://gitlab.lab.test
```

Получаем `301 Moved Permanently` и перенаправление на HTTPS. Затем обращаемся к странице входа с проверкой сертификата через наш CA.

```bash
curl --cacert "$PWD/certs/ca.crt" \
  --max-time 20 \
  -o /dev/null \
  -sS \
  -w '%{http_code}\n' \
  https://gitlab.lab.test/users/sign_in
```

На рисунке 9 видны оба результата. HTTP перенаправляется, HTTPS-запрос получает `200`. Проверку сертификата мы не отключаем, TLS-чек проходит штатно 🙂

![Рисунок 9 — Перенаправление HTTP и проверка HTTPS](https://raw.githubusercontent.com/KellyLamb123/Adm.Inf.Sys./main/lab6/screenshots/9.png)

Дальше выводим `admin-allow.conf` и снова обращаемся к `/admin` из временного контейнера.

```bash
cat nginx/admin-allow.conf
```

```bash
docker run --rm \
  --network lab6-net \
  -v "$PWD/certs/ca.crt:/ca.crt:ro" \
  curlimages/curl:8.12.1 \
  --cacert /ca.crt \
  --max-time 20 \
  -i \
  https://gitlab.lab.test/admin
```

На рисунке 10 видно разрешение для `172.30.6.1` и запрет остальных адресов. Проверочный контейнер получает `403 Forbidden` от nginx. Доступ с другого адреса закрыт.

Для проверки rate limiting отправляем двенадцать запросов подряд.

```bash
for i in {1..12}; do
```

На рисунке 11 первые шесть запросов проходят с `200`. Начиная с седьмого получаем `429`. Лимит с допустимым всплеском отрабатывает, запросы успешно притормозили 🙂

## Часть 6 — Подключаем Grafana к тому же SSO

Для Grafana используем клиент `grafana` из realm `lab6`. В Compose передаём адреса авторизации, обмена токенов и получения данных пользователя. Включаем PKCE и подключаем сертификат CA.

Пользователю, который входит через этот провайдер, назначаем роль `Viewer`. Для просмотра подготовленного dashboard этого достаточно.

## Часть 7 — Собираем мониторинг nginx

Для мониторинга выбираем nginx, через который проходят запросы к приложениям стенда.

В nginx открываем внутренний `stub_status` на порту 8080. nginx-exporter читает его и отдаёт метрики в формате Prometheus. Prometheus собирает данные каждые пять секунд.

### Настраиваем панели dashboard

Dashboard создаём через `monitoring/make_dashboard.py`. Скрипт формирует JSON, а Grafana подхватывает его через provisioning. Конфиг панелей хранится в репозитории, поэтому dashboard можно восстановить вместе со стендом.

Добавляем шесть панелей.

Для доступности nginx используем метрику

```promql
nginx_up
```

Для проверки самого сбора метрик добавляем

```promql
up{job="nginx"}
```

Скорость запросов отображаем через

```promql
rate(nginx_http_requests_total[1m])
```

Число активных соединений берём из

```promql
nginx_connections_active
```

Для оценки соединений, которые nginx принял, но не обработал, используем разницу приростов счётчиков

```promql
increase(nginx_connections_accepted[1m])
-
increase(nginx_connections_handled[1m])
```

Активные алерты выводим запросом

```promql
ALERTS{alertstate="firing"}
```

После серии запросов смотрим на dashboard. На рисунке 14 обе панели доступности показывают `1`, на графике запросов заметен рост, а число активных соединений меняется со временем.

Разница принятых и обработанных соединений остаётся нулевой. Панель алертов показывает `No data`, поскольку в этот момент активных срабатываний нет. Графики уже живые, мониторинг перестал быть просто набором конфигов 🙂

### Выбираем три правила алертов

В `monitoring/alerts.yml` описываем три правила и привязываем каждое к конкретной проблеме стенда.

Первое правило `NginxOrExporterUnavailable` проверяет доступность nginx и exporter. Если одна из проверок показывает ноль в течение 15 секунд, алерт срабатывает.

Недоступность nginx мешает входу в приложения. Остановка exporter лишает нас актуальных метрик. Для дежурного это повод проверить, какая часть цепочки отвалилась.

Второе правило `NginxActiveConnectionsHigh` срабатывает при количестве активных соединений больше 100 в течение 30 секунд.

Эта метрика помогает заметить рост нагрузки или накопление долгих соединений. Порог выбираем учебный, под наш стенд. Для рабочего сервиса его пришлось бы настраивать по реальным графикам нагрузки.

Третье правило `NginxDroppedConnections` проверяет разницу между приростами принятых и обработанных соединений.

Положительная разница может указывать на достижение ограничений обработки соединений. Такой алерт помогает заметить проблему до того, как жалобы пользователей заполнят чат поддержки 😅
